Confidential Computing protects the confidentiality of data in use and the integrity of workloads within a defined trust boundary.
The protected assets include code, models, secrets, and data.
Confidential Bare Metal (CBM), Confidential Virtual Machines (CVM), and Confidential Containers place that boundary at different layers of the infrastructure.

Use this comparison to understand which actors each modality excludes and which components the model owner must still trust.
For deployment choices, refer to [Deployment Modalities](./positioning).

## Who Controls Each Layer

In the deployments shown below, the model owner is the tenant.
The tenant controls the host OS, the guest OS, or the container workload.
Tenant-controlled components are trusted within the depicted threat model.
Other tenants are separate consumers of the infrastructure.

## How the Boundaries Differ

| Dimension | Confidential Bare Metal | Confidential VM | Confidential Containers |
| --- | --- | --- | --- |
| Model owner receives | Dedicated hosts and control of the assigned NVLink fabric | A confidential VM | A Kubernetes pod in a confidential VM |
| Host OS administrator | Model owner | Infrastructure owner | Infrastructure owner |
| Primary adversary | Infrastructure administrator with out-of-band or physical access | Privileged host software and other tenants | Kubernetes administrator, in addition to host administrators and other tenants |
| Hardware protection | DRTM measured launch and GPU Confidential Computing | CPU TEE for the VM and GPU Confidential Computing | CPU TEE for the pod's VM and GPU Confidential Computing |

Dynamic Root of Trust for Measurement (DRTM) establishes a measured launch of the host OS in the CBM configuration.
A CPU trusted execution environment (TEE) isolates a confidential VM from privileged host software.
The hardware protection for Confidential Containers uses the same VM isolation principle as CVM.

### Confidential Bare Metal

The tenant controls the host OS and workload on dedicated infrastructure.
Platform security controls and attestation address infrastructure administrators' management and physical access within the supported platform's threat model.
The tenant's host administrators and software inside that environment remain trusted.

### Confidential VM

The infrastructure owner administers the host OS and hypervisor; the tenant controls the guest OS, drivers, and workload.
The CPU TEE and GPU Confidential Computing protect the workload from privileged host software within the supported platform's threat model.
Guest software and any administrators with access inside the guest remain trusted.

### Confidential Containers

The infrastructure owner operates the Kubernetes control plane.
Each confidential pod runs inside a confidential VM, where an agent security policy constrains requests originating from the control plane.
The tenant must approve the workload and policy and bind secret release to that approved configuration.
For policy details, refer to [Securing Your Workload](https://confidentialcontainers.org/docs/getting-started/securing-workloads/).

## Attestation and Secret Release

Before releasing secrets, the tenant must verify the required platform, GPU, and software evidence against its policy and establish that the approved workload and configuration will receive them.
Attestation provides evidence about the environment; attestation does not establish that approved code is free of vulnerabilities.
Refer to [NVIDIA Attestation](https://docs.nvidia.com/attestation/) for attestation concepts and services.

## What Remains Outside These Protections

- **Availability:** Infrastructure owners can interrupt power, networking, scheduling, or workload execution.
  None of the three modalities guarantees availability against the infrastructure owner.
- **Behavior inside the trusted workload:** Vulnerable code, permitted debugging, and sensitive logging can expose protected assets.
  Protecting end-user data from the model owner requires additional controls over workload behavior and administrative access.
- **Physical attacks and side channels:** Coverage depends on the platform, interconnect, and security mode.
  Do not infer protection for every physical attack from the deployment modality alone.

For the underlying assumptions, refer to the [Confidential Containers trust model](https://confidentialcontainers.org/docs/architecture/trust-model/trust-model/) and the [NVIDIA CVM trust and threat model](https://docs.nvidia.com/enterprise-reference-architectures/deploying-proprietary-models-confidential-compute-self-hosted-vms/latest/trust-and-threat-model.html).
