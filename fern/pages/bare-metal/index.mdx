The Confidential Bare Metal (CBM) deployment modality provides NVIDIA Confidential Computing for tenant-dedicated bare-metal hosts.
In CBM, the model owner receives the whole host and operates the software infrastructure inside the model owner's own trust boundary.
For a comparison of CBM with the other modalities, refer to [Deployment Modalities](/confidential-computing/positioning).

CBM does not use a CPU trusted execution environment, because no separate host tenant exists to isolate the workload from.
Instead, CBM provides attested platform integrity and defense-in-depth protection through the following mechanisms:

- Platform attestation.
- GPU Confidential Computing protections.
- Platform security controls.

## Intended Audience

CBM is designed for organizations that build and operate their own software infrastructure on dedicated hardware.
CBM is appropriate for an organization that meets the following conditions:

- The organization receives entire hosts as a single tenant and manages the hosts directly.
- The organization builds, signs, and maintains a custom operating system image.
- The organization operates the infrastructure for workload launch, multi-node bootstrapping, and NVLink partitioning.
- The organization develops and operates an appraisal software for attestation, which can include a custom verifier.

If your workloads run on infrastructure that a provider operates, refer to [Confidential Virtual Machine](/confidential-computing/cvm) or [Confidential Containers](/confidential-computing/containers).

## Personas and Responsibilities

CBM divides responsibilities between the provider or operator and the model owner or AI lab.
The following table describes each persona and the responsibilities of that persona in a CBM deployment:

| Persona | Description | Responsibilities in CBM |
| --- | --- | --- |
| Provider or operator | The organization that owns or operates the host infrastructure. | Procures the systems from one or more OEMs, installs the system firmware, and delivers dedicated hosts to the model owner. |
| Model owner or AI lab | The organization that owns the model, the workload, the data, the keys, the attestation policy, and the security requirements. | Builds the operating system image, configures the hardware and the GPUs, operates the software infrastructure, and appraises the attestation evidence. |
| Tenant end user | The downstream user or application tenant whose prompts, inference inputs, inference outputs, and application data require protection. | No direct responsibilities. The protection for tenant end-user data depends on how the model owner deploys the workload. |

## Trust Boundary

After the model owner receives the dedicated host and verifies the platform state and the GPU state, the provider is outside the runtime trust boundary.
The model owner remains responsible for operating the software infrastructure.

CBM does not protect tenant end-user data from the model owner.
To protect tenant end-user data from the model owner, the model owner must deploy an additional virtualized Confidential Computing layer inside the bare-metal trust boundary.

## Deployment Workflow

A CBM deployment follows these high-level stages:

1. The provider sets up systems from one or more OEMs with the provider's UEFI firmware.
1. The model owner prepares a signed operating system image on a secure build server.
   The image contains the NVIDIA drivers and follows the NVIDIA reference image guidelines.
1. The model owner configures the hardware, installs the operating system image, and sets the confidential compute mode of every GPU to Bare-Metal Secure AI by using the [NVIDIA GPU admin tools](https://github.com/NVIDIA/gpu-admin-tools).
   The confidential compute mode takes effect after the next GPU reset.
1. The model owner operates the infrastructure for creating NVLink partitions and for launching single-node and multi-node workloads.
1. The model owner's software infrastructure performs multi-node bootstrapping, appraises the hardware and the software, and sets up the keys for NVLink encryption.
   The software infrastructure can integrate with the NVIDIA Multinode Confidential Computing Daemon (`nvidia-mnccd`) for these tasks.

## Platform Security Controls

The model owner manages the following controls to set up a CBM environment:

| Control | Purpose | How the model owner enables the control |
| --- | --- | --- |
| Dynamic Root of Trust for Measurement (DRTM) | Provides a hardware-rooted, measured launch of the operating system. | Applies the NVIDIA operating system kernel patches that enable a secure boot with DRTM. |
| CPU memory encryption | Encrypts CPU DRAM. | Enables CPU DRAM encryption at boot time in the BIOS setup. |
| NVLink encryption | Protects the data that moves between GPUs over NVLink and through NVLink Switches. | Enables NVLink encryption as a persistent GPU setting by using the NVIDIA GPU admin tools. |
| Confidential compute mode | The Bare-Metal Secure AI mode activates firewalls in the PCIe path that protect the contents of GPU memory. | Sets the confidential compute mode to Bare-Metal Secure AI as a persistent GPU setting by using the NVIDIA GPU admin tools. |

## Attestation

NVIDIA provides reference integrity manifests (RIMs) for the components that NVIDIA delivers: the CPU firmware, the GPU firmware, and the GPU microcode.
The model owner owns all other software that runs on the CPU, including the operating system kernel and the kernel drivers.
NVIDIA cannot attest the software that the model owner owns.

The model owner is responsible for the attestation infrastructure, which includes the following tasks:

- Appraising the attestation evidence for the hardware and the software.
- Attesting multiple nodes.
- Attesting the operating system and the model owner's software infrastructure.

## Threats and Mitigations

The following table compares how a conventional hypervisor, a confidential virtual machine (CVM), and CBM address each threat:

| Threat | Description | Conventional hypervisor | CVM | CBM |
| --- | --- | --- | --- | --- |
| Untrusted UEFI or BIOS | The system firmware is not trusted. | Not protected | Protected | Protected by DRTM |
| Physical attacks on NVLink | An attacker launches a physical attack on NVLink. | Not protected, or optionally protected | Protected | Protected by NVLink encryption |
| Physical or software attacks on NVLink Switches | An attacker launches a hardware-based or software-based attack on an NVLink Switch. | Not protected | Protected by NVLink encryption | Protected by NVLink encryption |
| Physical attacks on PCIe | An attacker launches a physical attack on the PCIe bus. | Not protected | Protected. Active physical bus attacks are out of scope. | Protected by GPU Confidential Computing protections. Active physical bus attacks are out of scope. |
| Physical attacks on the CPU-to-GPU interconnect | An attacker launches a physical attack on the chip-to-chip (C2C) interconnect between the CPU and the GPU. | Not protected | Protected | Not protected |
| Compromised hypervisor | An attacker compromises the hypervisor. | Not protected | Protected | Not applicable. CBM has no hypervisor layer. |

## Engaging NVIDIA

CBM deployments require significant investment in infrastructure and attestation by the model owner.
NVIDIA works directly with each organization that adopts CBM.
To discuss a CBM deployment, contact your NVIDIA account team.
